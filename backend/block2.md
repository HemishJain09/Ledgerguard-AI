# Ledger Guard: Phase 2 (Candidate Generation & Graph Construction)

## Overview
Phase 2 of Ledger Guard takes the pristine, standardized data generated by the Phase 1 Ingestion Pipeline (the `FactLedger`) and transforms it into a highly optimized, strictly bounded graph.

In enterprise reconciliation, the naive approach of comparing every single transaction against every other transaction creates an $O(N \times M)$ search space. This leads to massive performance bottlenecks and freezes the optimization solvers. Phase 2 acts as a **Deterministic Sieve**, aggressively pruning impossible matches and isolating the remaining ambiguous matches into tiny, mathematically independent puzzles (disjoint subgraphs) for the downstream MILP solver (Phase 3).

## Architecture & Data Flow

The pipeline is entirely deterministic and relies on strict engineering bounds:

### Block 1: Financial Event Builder
- **Goal:** Elevate raw, atomic database facts into concrete economic events.
- **Mechanism:** The builder groups the exploded `FactLedger` rows (e.g., Gross, Fee, Tax atoms) back together using their `transaction_id` and `source_file_hash`. It then creates specific representations based on the reconciliation goal:
  - **SALE_EVENT (ERP):** Amount is set to the true *Net Invoice Total* so it perfectly matches the Payment Gateway's gross receipt.
  - **PG_PAYMENT_EVENT (PG vs ERP):** Amount is the Gateway's Gross amount.
  - **PG_PAYOUT_EVENT (PG vs Bank):** Amount is the Gateway's Net amount (Gross - Fees - Tax).
  - **BANK_SETTLEMENT_EVENT (Bank):** Amount is the Bank's credited Net amount.

### Block 2: The Job & Policy Scope
- **Goal:** Define strict boundaries for the reconciliation job to ensure the system never makes assumptions outside of an audited envelope.
- **Mechanism:** Powered by a centralized `config.yaml`, the policy enforces the `target_currency` (e.g., "INR"), the `max_settlement_lag_days` (e.g., 7 days), and the `fuzzy_match_threshold`.

### Block 3: The Generation Funnel
- **Goal:** Act as the master gateway for deterministic reduction, slashing the $O(N \times M)$ search space.
- **Mechanism:** The funnel applies a strict three-step sieve to pairs of events:
  1. **Merchant & Currency Partition:** A hard partition. Any pair with mismatched currencies is immediately discarded. (The system dynamically extracts symbols like `$` or `₹` from raw strings to defeat LLM hallucinations).
  2. **Temporal Window Pruning:** Calculates the absolute time difference ($\Delta t$) between events. If the lag exceeds the policy threshold (accounting for timezone fuzziness across UTC and IST), the pair is discarded.
  3. **Token & Amount Evidence:** Calculates math differences and Jaccard-style string overlap (via `thefuzz`). If the amounts match exactly, or the fuzzy token score exceeds the threshold, a `ReconEdge` is formally generated.

### Block 4: Multi-Signal Resolution & Clustering
- **Goal:** Package the surviving candidate edges into isolated, computationally feasible chunks.
- **Mechanism:** The pipeline uses `NetworkX` to draw the graph. Every event is a node, and every surviving `ReconEdge` connects them. Finally, it extracts the **Connected Components**.
- **Why this matters:** A connected component is a disjoint subgraph. It means the events inside the cluster have *zero* relationship to any event outside of it. The downstream MILP solver can process these 60+ tiny clusters completely in parallel, preventing global lockups.

## Conclusion
With Phase 2 complete, Ledger Guard has bridged the gap between static database rows and complex mathematical optimization. The graph pipeline correctly identifies exact matches, safely traps ambiguities (like overlapping amounts or same-day split settlements), and prepares perfectly isolated payloads. We are now ready to unleash the MILP Solver Engine for Phase 3!
